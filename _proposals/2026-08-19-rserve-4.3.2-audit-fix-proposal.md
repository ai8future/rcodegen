# rserve 4.3.2 Hardening — Callback Routing, Async Admission, Lifecycle, and Artifact Bounds

**Date:** August 19, 2026  
**Status:** Proposed  
**Recommended release:** 4.3.3  
**Origin:** Second-pass audit of the 4.3.0–4.3.2 async callback, run-retention, clone-artifact, and callback-SSRF changes.

## Executive decision

Do not treat 4.3.2 as complete. Ship one patch release that:

1. makes plaintext callbacks bypass ambient HTTP proxies so the delivery-time private-address check cannot inspect the proxy instead of the callback host;
2. adds bounded admission for live async work before returning `202`;
3. makes terminal state, retained result, and callback ownership one atomic decision;
4. routes gRPC cancellation through the async run owner so an acknowledged cancellation cannot later report success; and
5. bounds artifact inspection work independently of the response-size and skip-report caps.

The first two items are release blockers. The lifecycle and artifact items should land in the same patch because they affect the correctness and availability guarantees introduced by 4.3.0 and 4.3.1, and the necessary code surfaces are already under active change.

## Goals

- Preserve the advertised 4.3.2 callback policy under real deployment environments, including `HTTP_PROXY`.
- Put a predictable upper bound on server-owned queued work and retained request payloads.
- Guarantee that exactly one terminal outcome owns all three representations of a run: status, retained result, and callback payload.
- Make HTTP `DELETE` and gRPC `CancelRun` agree for queued and running async runs.
- Prevent artifact collection from turning bounded output into disproportionate filesystem I/O.
- Add regression tests that fail under each audited defect, including race and adversarial transport tests.

## Non-goals

- Durable async storage. The caller remains responsible for durable state; rserve retention stays in-memory.
- Changing the documented meaning of async `success`: a nonzero CLI exit may still be a completion when the synchronous path would return that completion. This proposal fixes cancellation classification, not that compatibility rule.
- Following callback redirects or widening plaintext address policy.
- Reworking the earlier 4.2.12 clone-validation findings; they are outside this audit proposal.
- Increasing artifact payload limits or returning binary artifacts.

## Finding 1 — Plaintext callback policy is bypassed by environment proxies

### Problem

`newCallbackClient` clones `http.DefaultTransport`, which retains `Proxy: http.ProxyFromEnvironment`, and replaces only `DialContext` for the plaintext client (`pkg/server/openai/asyncruns.go:301-305`). When `HTTP_PROXY` selects a proxy, Go asks `DialContext` to connect to the proxy. `dialPlaintextCallback` therefore resolves and approves the proxy host rather than the callback URL host.

A private or loopback proxy can then receive the absolute callback URL and resolve or forward it itself. This reopens the public-address/DNS-rebinding path that 4.3.2 says is closed, and can expose the completion, artifacts, and caller-supplied callback headers. A nonfunctional proxy already reproduces the routing error: with `HTTP_PROXY=http://127.0.0.1:1` and `NO_PROXY=` the private-host callback test performs zero deliveries and reports a proxy connection failure.

### Required change

- In the callback-client constructor, set `transport.Proxy = nil` whenever the private-address `DialContext` is installed.
- Keep HTTPS behavior unchanged for this patch: HTTPS remains allowed to any host with default TLS validation and may retain standard proxy behavior. Document that distinction explicitly.
- Do not add a fallback that retries through the default transport. A failed direct plaintext delivery must remain failed and pollable.

### Tests

1. Set `HTTP_PROXY` and `http_proxy` to a working `httptest` proxy, clear `NO_PROXY`, and deliver to a private-resolving hostname. Assert:
   - the callback receiver is hit once;
   - the proxy is hit zero times; and
   - `callbackDialIP` receives the vetted callback address.
2. Repeat the DNS-rebinding test with the proxy variables set. Assert no proxy or public target is reached.
3. Keep the existing no-redirect and split-private/public resolution tests.

### Acceptance criterion

Every plaintext callback connection is a direct connection to an address returned and approved by `callbackLookupIP` during that attempt; ambient proxy variables cannot change the dial target.

## Finding 2 — Live async admission is unbounded

### Problem

`asyncRuns.submit` always retains a run, and `submitAsyncRun` always returns `202` and starts a goroutine. The result count and TTL limits apply only after terminalization; queued and running runs are deliberately never evicted. The registry counts waiters but does not cap them.

Unlike synchronous requests, accepted async work survives the submitting connection. A caller can therefore accumulate an arbitrary number of goroutines and retained plans. Each plan can retain a task near the 10MB request limit plus work-directory strings, callback URL, and callback headers. The current “100 results or one hour” statement is not an admission bound and does not protect the live set.

### Required change

Add two admission limits owned by `asyncRuns` and enforced under its mutex before a run ID is published:

- **Live-run count:** default `max(8, 4 * max_concurrent)`.
- **Retained-plan bytes:** default 64 MiB, conservatively estimated from task, callback URL/header strings, model/session strings, and work-directory strings.

Expose overrides at rserve startup as:

- `RSERVE_ASYNC_MAX_LIVE`
- `RSERVE_ASYNC_MAX_BYTES`

Invalid or non-positive configured values should fail startup rather than silently disabling protection. Pass parsed limits into `NewHandler`/`newAsyncRuns`; do not read deployment configuration from request-handling code.

Change `submit` to return either an admitted run or a capacity error. Capacity must be reserved before `writeJSON(..., 202, ...)`. On refusal return:

- HTTP `503`;
- `Retry-After: 1`;
- error code `async_capacity`;
- `retryable: true`; and
- no run ID and no goroutine.

Release count and byte reservations exactly once when the async execution goroutine no longer retains the plan. Result retention remains governed separately by the existing 100-result/one-hour policy.

### Why both limits are needed

A count-only bound still permits several maximum-size requests to consume excessive memory. A byte-only bound permits a large number of tiny requests and goroutines. Count plus approximate retained payload bytes bounds both failure modes without pretending to be an exact Go heap accounting system.

### Tests

1. Hold the only run slot, admit requests through the live-count limit, then assert the next request returns retryable `503` without adding a run, waiter, or goroutine.
2. Use a small test byte budget and assert a large task is rejected while smaller tasks are accepted.
3. Cancel and complete admitted runs; assert reservations are released exactly once and new work can be admitted.
4. Exercise concurrent submit/cancel/finish under `-race`, checking that neither counter becomes negative or exceeds its configured bound.
5. Assert shutdown does not create more live callback goroutines than the admitted live-run bound.

### Acceptance criterion

At all times, accepted nonterminal async runs are within both configured limits, and capacity rejection occurs before a `run_id` or `202` is emitted.

## Finding 3 — Terminal state and callback ownership are not atomic

### Problem

The worker records its terminal result through `finish` and separately enters `deliverOnce`. Shutdown snapshots live runs, cancels them, and independently enters the same `deliverOnce` with a `server_shutdown` payload. `sync.Once` prevents two callback attempts but does not ensure that the callback payload matches the status/result retained by `finish`.

If a run finishes naturally after shutdown snapshots it but before the competing callback wins, a receiver can get `server_shutdown` even though the run stored success. That false retryable failure can cause duplicate work in the external orchestrator.

### Required change

Replace the split `finish`/`deliverOnce` decision with one store-owned terminalization primitive:

```go
func (a *asyncRuns) tryTerminalize(run *asyncRun, status string, payload *AsyncCompletion) bool
```

Under `asyncRuns.mu`, it must:

1. accept transitions only from `queued` or `running`;
2. set terminal status, finish time, retained result, and last-access time;
3. apply retention bounds; and
4. return `true` only to the caller that won terminal ownership.

Only the winner may dispatch the callback, and it must dispatch the same logical payload selected by terminalization. A later worker completion or shutdown attempt must not overwrite the result or send a different outcome. `sync.Once` may remain as defensive protection, but it must no longer be the state machine.

Cancellation cause should be explicit rather than inferred from unrelated contexts:

```text
none | caller_http | caller_grpc | server_shutdown
```

HTTP and gRPC caller cancellation both produce `run_cancelled`; shutdown produces `server_shutdown`. The cause is set once under the same mutex before cancellation is signaled.

### Shutdown ordering

1. Stop HTTP acceptance and wait for request handlers, as today.
2. Mark the async store as closing so no direct test or future caller can submit after shutdown begins.
3. Set `server_shutdown` cause and cancel live contexts.
4. Attempt terminalization of still-live runs with the shutdown payload.
5. Deliver only for shutdown transitions that won.
6. Wait within the existing budget for execution goroutines to reap children and remove clones.

### Tests

1. Race natural completion against shutdown repeatedly; callback and retained result must always have identical status and error code.
2. Assert exactly one terminal transition and one callback attempt per run.
3. Assert a run terminalized successfully immediately before shutdown is not sent a shutdown failure.
4. Assert a shutdown winner cannot later be overwritten by worker success or cancellation output.
5. Run the lifecycle race tests with `-race -count=100` as a targeted stress check.

### Acceptance criterion

For every run ID, status, retained result, and delivered callback describe one terminal outcome chosen by one atomic transition.

## Finding 4 — gRPC cancellation does not use the async run owner

### Problem

The HTTP and gRPC servers share `RunRegistry`. Once an async run acquires a slot, gRPC `CancelRun` finds the published ID and cancels the acquisition's child context. The async worker later checks its parent `run.ctx`, which remains uncancelled, so the acknowledged cancellation can be classified as an ordinary completion and delivered as success. Before slot acquisition, the run is absent from the registry and gRPC reports it as not found.

The shared ID is therefore cosmetic rather than a complete cross-protocol cancellation contract.

### Required change

Make the async store the cancellation authority for async IDs:

- Inject an async cancellation callback/interface into the gRPC server from `cmd/rserve/main.go`, avoiding a `server` → `openai` import cycle.
- In gRPC `CancelRun`, consult the async owner first. If it owns the ID, set cause `caller_grpc` and cancel the async parent context. Otherwise fall back to `RunRegistry.Cancel` for ordinary gRPC/HTTP synchronous runs.
- Keep HTTP `DELETE /v1/runs/{id}` on the same `requestCancel` primitive with cause `caller_http`.
- A queued async ID must be cancellable through either HTTP DELETE or gRPC, with the same callback/result semantics.
- A terminal async ID should remain idempotent according to the existing HTTP contract; gRPC should return a clear “already terminal” result rather than claiming it killed active work.

If queued async visibility is not added to gRPC `GetStatus` in this patch, correct the changelog/API wording to state that gRPC status lists acquired/active registry runs while `/v1/runs` owns the full async lifecycle. Do not continue claiming full status parity when the proto cannot express queued async state.

### Tests

1. Saturate the registry, submit an async run, cancel it through the gRPC method while queued, and assert a `run_cancelled` callback/result with no CLI start.
2. Cancel a running async run through gRPC; assert:
   - `Cancelled: true`;
   - CLI child termination;
   - callback/result status `failure` with code `run_cancelled`;
   - clone cleanup; and
   - slot release.
3. Race HTTP DELETE and gRPC cancellation. Exactly one cause/transition wins and only one callback is sent.
4. Verify ordinary non-async registry cancellation remains unchanged.

### Acceptance criterion

Any API that reports an async run was cancelled causes that run to terminate as `run_cancelled`; it can never subsequently publish success.

## Finding 5 — Artifact response caps do not bound artifact inspection work

### Problem

The collector loops through every changed path, reads an eligible file in full, and only then calls `looksTextual`. Binary files do not consume the returned-artifact count or content budget. The skip report stops growing at 100 entries, but collection continues reading.

With the 200,000-entry clone scan limit and 512KB per-file read limit, a run can create 200,000 hard links to one 512KB binary file and cause approximately 100GB of repeated reads while using little data-block storage. Collection holds the run slot and has no independent candidate-count or read-byte budget.

### Required change

Introduce an artifact inspection budget separate from output limits:

- maximum candidate files inspected: 1,000;
- maximum aggregate bytes read during classification and collection: 16 MiB; and
- existing response limits remain 100 artifacts, 512KB per file, and 2 MiB returned content.

For each candidate:

1. charge and read only the text probe first;
2. reject binary content without reading the remainder;
3. for text files, reserve the advertised file size against the remaining inspection and response budgets before reading the full file;
4. verify the opened handle is still a regular file before reading, so a scan/read type change cannot turn collection into a FIFO/device wait; and
5. stop additional reads when either inspection budget is exhausted.

Add `inspection_cap` as an artifact skip reason. Report individual paths until the existing skip-report cap, then retain the existing dropped-skip log summary. The run itself must still succeed.

Keep the budget constants package-level variables only where tests need to shrink them; production mutation is not supported.

### Tests

1. Create many binary hard links with a reduced test budget and instrument reads. Assert aggregate bytes and candidates never exceed the configured inspection limits.
2. Put a valid text artifact after many binary candidates. Assert either it is returned within budget or explicitly named `inspection_cap`; it must not disappear silently.
3. Replace a scanned regular candidate with a FIFO/non-regular entry before open and assert collection returns `collection_error` or an explicit non-regular skip without blocking.
4. Retain the existing exactly-at-cap, response-cap, too-many-files, scan-limit, and callback-retention tests.
5. Assert artifact collection still runs before clone cleanup on success, failure, and cancellation.

### Acceptance criterion

One run's artifact collection performs at most 1,000 candidate inspections and 16 MiB of file reads, irrespective of clone entry count, binary-file count, hard links, or skip-report truncation.

## Verification matrix

### Targeted

```bash
go test -race -count=1 ./pkg/server/openai ./pkg/server
go test -race -count=100 -run 'TestAsync.*(Shutdown|Cancel|Terminal)' ./pkg/server/openai
HTTP_PROXY=http://127.0.0.1:1 NO_PROXY= go test -count=1 -run 'TestAsyncCallback' ./pkg/server/openai
```

The proxy test suite must use both a dead proxy and a working recording proxy. A dead proxy proves it is ignored; a working proxy proves callback payloads and headers never reach it.

### Repository-wide

```bash
go mod vendor  # only if local replace directives are present
gofmt -w <changed-go-files>
go vet ./...
go test -race ./...
make
```

### Operational smoke check

1. Start rserve with one run slot and small async admission limits.
2. Hold the slot, fill async capacity, and verify the next submission receives retryable `503` without a run ID.
3. Release one run and verify a new submission is admitted.
4. Deliver a plaintext callback to a private-resolving hostname while `HTTP_PROXY` points at a recording proxy; verify direct receiver delivery and zero proxy traffic.
5. Cancel one queued and one running async run through gRPC; verify both callbacks are `run_cancelled` failures.
6. Begin shutdown at a controlled completion boundary; verify callback and recorded terminal outcome agree.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Deployments unknowingly relied on `HTTP_PROXY` for plaintext LAN callbacks | This behavior conflicts with the private-address security contract. Document direct-only plaintext delivery and require HTTPS for proxy-routed callbacks. |
| New admission defaults are too small for bursty workloads | Make both limits startup-configurable, expose current live count and configured cap in `/health`, and return retryable `503` before acceptance. |
| Lifecycle refactor drops partial cancellation artifacts | Keep HTTP/gRPC cancellation as a cause-setting operation; let the worker collect artifacts before it attempts terminalization. Only shutdown may terminalize immediately without waiting for artifacts. |
| Terminalization and retention copies diverge | Store the selected logical payload once; derive the bounded retained copy deterministically while holding terminal ownership. Tests compare status/error identity, while documented artifact-content eviction remains allowed. |
| Inspection budget hides a desired artifact late in sort order | Return explicit `inspection_cap` skips, keep deterministic path ordering, and make the inspection limits visible in documentation. |
| Added configuration silently parses incorrectly | Parse once at startup, reject invalid values, and log effective limits in the existing startup record. |

## Definition of done

- The working-proxy regression test proves plaintext callback data never reaches an environment proxy.
- Async live count and estimated retained-plan bytes cannot exceed configured limits under concurrent `-race` tests.
- Capacity rejection occurs before `202` and contains no run ID.
- Callback, retained result, and status always agree on the terminal outcome.
- HTTP and gRPC cancellation both produce `run_cancelled` for queued and running async runs.
- Artifact collection obeys candidate and read-byte budgets and cannot block on a changed non-regular file.
- Targeted race stress, full race suite, `go vet ./...`, and `make` pass.
- VERSION, CHANGELOG, API/README, and `_bugs_fixed` are synchronized for 4.3.3.

## Recommended review posture

Request changes unless all five invariants above are covered by executable tests. In particular, passing the existing suite is insufficient: 4.3.2's suite passes while ambient proxy routing remains active, live async admission remains unlimited, and callback ownership remains separate from terminal-state ownership.
